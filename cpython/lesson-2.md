# Lesson 2: The CPython Build Pipeline

As a C programmer, you already know how compilation and linking work. However, CPython’s build system has some unique quirks—especially around **bootstrapping** and **code generation**—that often trip up new contributors. This lesson breaks down the entire pipeline so you can build, debug, and modify CPython with confidence.

---

## 1. Lesson Overview

In this lesson, we trace how the C source files from Lesson 1 are compiled, linked into a core library, and combined with extension modules to produce the final `python` executable.

**Why it matters:**  
To hack on CPython, you must know:
- How to build a **debug version**.
- How to **recompile** after changing a core object *vs.* a standard library module.
- Which files you are **allowed to edit** (and which are **auto‑generated**).

**Prerequisites:**  
You understand C compilation, object files (`.o`), static/shared libraries (`.a`/`.so`), and Makefiles.

---

## 2. Mental Model – The Build Pipeline

CPython’s build is a **multi‑stage pipeline**. The most important insight:  
> **CPython uses Python to build Python.**

```
[1. Config]    ./configure ─────────────► Makefile
                                            │
[2. Bootstrap] Existing Python              │
               generates C code ────────────┤
               (AST, parsers, clinic)       │
                                            ▼
[3. Core]      GCC compiles Python/         │
               Objects/, Parser/ ─────────► libpython (Static or Shared)
                                            │     │
                                            │     ▼
[4. Link]      GCC compiles Programs/       │   python executable
               python.c and links it ───────┘
                                            │
[5. Exts]      Newly built 'python'         │
               compiles Modules/ ─────────► .so / .pyd (C Extensions)
```

---

## 3. Where We Are in the Repository

| **Path**                     | **Purpose**                                                                 |
|------------------------------|-----------------------------------------------------------------------------|
| `/` (repository root)        | Contains the main build scripts and `Makefile.pre.in`.                      |
| `configure.ac`               | Source for the POSIX `configure` script.                                   |
| `Makefile.pre.in`            | Template that becomes the actual `Makefile`.                               |
| `pyconfig.h.in`              | Template for system‑specific `#define`s (generated as `pyconfig.h`).       |
| `PCbuild/`                   | Visual Studio project files for Windows (parallel build system).           |
| `Tools/build/`               | Python scripts that generate C code before compilation starts.             |

> **Why they matter:** POSIX uses autotools (`configure`); Windows uses MSBuild. Both accomplish the **same** C‑level compilation pipeline.

---

## 4. Concepts We Need First

### 4.1 Code Generation
CPython does **not** hand‑write every C file. Many C files are generated by Python scripts *before* the C compiler runs.  
For example, `Python/Python-ast.c` is generated from an Abstract Syntax Tree definition file (`.asdl`).  
**You never edit generated C code manually** – you edit the source definition and re‑run the generator.

### 4.2 Debug vs. Release Builds
By default, CPython builds highly optimised release binaries. As a CPython engineer, you will almost exclusively work with a **debug build**:
```bash
./configure --with-pydebug
make
```
This:
- Disables C compiler optimisations (`-O0`).
- Enables runtime assertions (`assert()`).
- Turns on memory‑tracking macros (to catch leaks and overflows).

---

## 5. Architecture – Core Library + Plugins

CPython is architected as a **core runtime library** plus **dynamically loaded plugins**:

1. **Core Runtime (`libpython`)**  
   - The VM, built‑in types (`Objects/`), and compiler (`Python/`).  
   - Compiled into one large library (e.g., `libpython3.14.a` or `libpython3.14.so`).

2. **The Executable (`python`)**  
   - A tiny wrapper (from `Programs/python.c`) that links against `libpython` and calls its `main()`‑equivalent.

3. **Extension Modules (`Modules/`)**  
   - Standard library C extensions (like `math`, `sqlite3`, `zlib`) are compiled as standalone shared objects (`.so` or `.pyd`).  
   - They are loaded dynamically **at runtime** only when you type `import math`.

---

## 6. Important Data Structures (Build System)

In `Makefile.pre.in`, these variables define the build:

| Variable         | Meaning                                                                                      |
|------------------|----------------------------------------------------------------------------------------------|
| `OBJS`           | List of all `.o` files that form the core runtime (e.g., `Objects/dictobject.o`, `Python/ceval.o`) |
| `LDLIBRARY`      | Name of the core library being built (e.g., `libpython3.14.a`).                              |
| `MODULE_OBJS`    | Object files for modules that are **statically linked** into the core (like `sys` or `builtins`), rather than dynamically loaded. |

These are defined in the Makefile template – you can inspect them directly.

---

## 7. Important Functions (Build System Entry)

### `Programs/python.c : main()`
- **Purpose:** The entry point of the binary.
- **What it does:** It does almost nothing. It immediately calls `Py_BytesMain()` (or `Py_Main`), which lives inside `libpython`. It exists merely to provide a standard C `main` function for the OS to execute.

```c
// Programs/python.c (simplified)
int main(int argc, char **argv) {
    return Py_BytesMain(argc, argv);
}
```

---

## 8. Important Macros

| Macro               | Description                                                                                                                                 |
|---------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| **`Py_DEBUG`**      | The most important macro for developers. When defined (via `--with-pydebug`), CPython adds hidden fields to `PyObject` to track references, enables `assert()` checks, and uses special memory allocators to catch leaks. |
| **`Py_GIL_DISABLED`** | When configured with `--disable-gil` (the new free‑threaded mode), this macro modifies structs across the codebase to replace simple counters with atomic variables and locks. |

---

## 9. Source Code Exploration – Blueprints

To understand the build, you don't read C code – you read the **blueprints**:

- **`configure.ac`** – The source of truth for POSIX build flags.  
  Search for `with-pydebug` to see how debug mode is enabled.

- **`Makefile.pre.in`** – The Makefile template.  
  - Look for `PYTHON_HEADERS` – this lists everything in `Include/`.  
  - Look for `LIBRARY_OBJS` – this is the exact list of C files compiled to build the runtime.

- **`Modules/Setup`** – A text file that dictates which C extension modules are compiled **statically** into `libpython` and which are compiled as **dynamic** shared objects.

---

## 10. Execution Flow – Step by Step

Trace what happens when you run:
```bash
./configure --with-pydebug && make
```

1. **`configure`** probes your OS, finds your C compiler (GCC/Clang), and generates:
   - `Makefile` (from `Makefile.pre.in`)
   - `pyconfig.h` (containing system‑specific `#define`s)

2. **`make`** executes the following phases:

   - **Bootstrapping:** `make` invokes an **existing Python interpreter** on your system to run scripts in `Tools/build/` that generate:
     - `Python/Python-ast.c` (from ASDL)
     - opcode definitions
     - Argument Clinic C code (for cleaner C‑API functions)

   - **Compilation (Core):** GCC compiles everything in `Objects/`, `Python/`, and `Parser/` into `.o` files.

   - **Linking (Core):** GCC links those `.o` files into `libpython.a` (or `libpython.so`).

   - **Executable:** GCC compiles `Programs/python.c` and links it against `libpython.a` to create the `python` binary.

   - **Extensions:** The newly built `python` binary executes a build script to compile the standard library C extensions (like `math.c`) into `.so` files stored in `build/lib.*/`.

---

## 11. Real Python Example – What Gets Rebuilt?

Suppose you add a `printf("Hello\n");` debug statement.

- **Scenario A:** You modify `Objects/listobject.c`.  
  When you run `make`, GCC recompiles `listobject.o`, rebuilds `libpython`, and relinks the `python` executable.

- **Scenario B:** You modify `Modules/mathmodule.c`.  
  When you run `make`, GCC **only** recompiles `math.so`.  
  `libpython` and the `python` executable are completely untouched.

---

## 12. Why This Design?

### Why bootstrapping?
Generating C code from Python scripts prevents human error.  
For example, the AST rules are defined in a clean `.asdl` text file; Python scripts read it and emit thousands of lines of boilerplate C struct definitions. This keeps the logic consistent and maintainable.

### Why dynamic extensions?
If CPython fails to compile the `sqlite3` C module because your Linux box is missing SQLite development headers, the core `python` compilation still succeeds. You get a working Python runtime – just without `sqlite3`. This decoupling makes CPython portable across many environments.

---

## 13. Common Beginner Mistakes

- **Mistake:** Modifying a generated file like `Python/Python-ast.c`, running `make`, and wondering why your changes vanished.  
  **Correction:** Always check if a C file has a header comment saying `/* Generated by ... */`. If it does, you must modify the **source** configuration file and re‑run the generator (e.g., `make regen-all`).

- **Mistake:** Benchmarking performance using a debug build.  
  **Correction:** `--with-pydebug` makes CPython **2× to 3× slower**. Never profile CPython unless you built it with optimisations enabled (`--enable-optimizations`, which uses Profile‑Guided Optimisation / PGO).

---

## 14. Summary

- CPython is built in **two major halves**:
  1. **Core runtime** (`libpython`) – contains the compiler, VM, and objects.
  2. **Dynamically loaded C extensions** (`Modules/`) – loaded on demand.
- The build relies heavily on **Python itself** to generate C boilerplate before the C compiler even runs.
- Development requires building with **`--with-pydebug`** to enable C‑level runtime checks.

## 16. Important Makefile Targets

| Target            | Purpose                                                                 |
|-------------------|-------------------------------------------------------------------------|
| `make regen-all`  | Runs **all** Python scripts that generate C code (AST, opcodes, clinic). |
| `make clean`      | Removes all `.o` files and forces a fresh build from scratch.           |

## 17. Important Structs (not build‑specific, but related)

The build system itself doesn't define C structs, but note that the macro **`Py_DEBUG`** radically alters structs like `PyObject` under the hood – adding extra fields for debugging.

## 18. Important Files – Quick Reference

| File                   | Role                                                                 |
|------------------------|----------------------------------------------------------------------|
| `configure.ac`         | POSIX configuration source (autotools).                              |
| `Makefile.pre.in`      | Makefile template – defines all build rules and variables.           |
| `pyconfig.h` (generated) | Contains all system‑specific `#define`s (e.g., `HAVE_PTHREAD`).    |
| `Modules/Setup`        | Decides static *vs.* dynamic linking for each C extension.           |
